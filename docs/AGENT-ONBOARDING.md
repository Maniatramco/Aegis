# Dataset onboarding in Aegis Agent

Dataset onboarding is a separate workflow, available to administrators from **Onboard dataset** in Aegis Agent or an explicit request such as “Onboard a new dataset named Research with model mapping.” LangGraph classifies the current request once and delegates onboarding, upload and extraction to **Onboard & Extract Agent**. That agent calls the validated preparation tool directly, without another model call to rediscover the operation. This proposes a form without creating a dataset. How-to questions retain the read-only application guidance route. Re-extraction and metadata answering retain their existing implementations.

Review the name, optional description and registered models for Embedding, Chat and Extraction. Models must be enabled, have the corresponding capability and have their connection credentials configured. A chat/extraction model can serve both roles. The default full workflow also collects 1–20 PDF/DOCX/TXT/JSON documents, a separately uploaded or entered strict JSON Schema prompt, optional extraction instructions, and independent or merged extraction (separate records or one combined record). Cloud connections require explicit external-processing consent. Uncheck document processing for configuration-only onboarding.

Confirming authorizes the complete selected setup. The shared horizontal stepper reports real stages: Validate setup → Create dataset → Map models → Save prompt → Upload documents → Index documents → Extract fields → Publish knowledge → Ready for review. Prompt validation and connection consent happen before dataset creation. Confirmed document filenames, sizes and SHA-256 hashes bind the upload to the reviewed files. Files are staged durably before processing so a browser reload does not require reattachment once accepted. A prompt JSON file is never indexed as a document through the prompt input.

Each server transition is saved in external storage with SQL record metadata. The setup uses a deterministic workflow ID from a personal request UUID, and a deterministic dataset ID. Replaying creation after an interrupted receipt reuses that dataset. Replaying mapping recognizes an identical completed mapping without incrementing its version. Final readiness checks the actual active dataset and all default roles. Existing model-mapping validation and optimistic version checks remain authoritative. Configuration changes to selected models during setup stop the run rather than silently changing the confirmed choices.

Failures retain a Retry onboarding workflow action. Retrying validates the whole setup and reuses committed creation/mapping, the identical saved prompt, upload receipts and extraction submission receipts. Failed/cancelled indexing is restarted using retained originals; failed extraction resumes its existing result with a new version. Completed sibling results are retained and can be reviewed. Model/dataset/prompt changes after confirmation stop processing instead of silently substituting inputs. An uncertain partially committed upload is surfaced by the existing upload API for inspection, rather than duplicating originals.

The worker continues every confirmed stage after documents are staged, including creation, model mapping and knowledge publication, independently of browser polling. The browser reads progress; only explicit retry posts to `/advance` with `retry: true`. Failed workflows never silently retry on a status read. Browser storage retains the confirmed request UUID even if the initial response is lost, preventing duplicate creation on another attempt. A definitive initial validation rejection lets the user correct the draft; a rejected file transfer retains the accepted workflow. If documents were not staged before interruption, reattach the identical confirmed files. The server exposes the user's last 20 saved onboarding workflows through `/api/agent-v2/onboarding`.

Completion verifies canonical JSON and Parquet results through the Parquet loader, synchronizes dataset/model/prompt/document/extraction knowledge, checks current content digests and acknowledges the expected vector IDs in the active provider. The receipt includes provider, collection, entity IDs, verified vector count and Parquet references. Active OCI configuration saves files in Object Storage and vectors in the native Oracle vector table; local configuration uses its configured local vector provider. No completion is reported if required publication fails. Existing-dataset upload/extract plans use the same publication check; **Retry knowledge update** republishes saved artifacts without creating another extraction job. Confirmed choices, access checks and saved versions remain authoritative.

Use dataset in Aegis Agent selects the configured dataset. Completed extraction cards expose Review buttons into the separate review page, with the existing return-to-agent navigation. The prompt and document/result metadata remain scoped to the newly created dataset and are available to existing chat tools. Dataset/model creation remains administrator-only, checked at every new API route and proposal tool. The workflow does not register models, grant access, change credentials or overwrite another dataset's mapping.

Chat proposals retain the saved onboarding workflow ID on the server plan, so reopening the plan restores its real setup even without a browser workflow cache. Completion replaces the original proposal reply with a verified receipt containing the actual dataset, prompt, document count and completed result count. `get_dataset_onboarding_status` reads personal history, actual progress/errors, model roles, filenames, prompt identity and extraction IDs; recent receipts are included in the verified chat snapshot. Completed setup cards show a compact read-only receipt instead of disabled form fields.

Implementation: `backend/app/agent_onboarding.py`, `frontend/app/agent-onboarding.tsx`, and agent routing/tool integration. Verification includes real storage/API tests for capability/access checks, replay after committed creation/mapping, and streamed/non-streamed graph proposals; component tests verify confirmation, duplicate-click protection, restored retries and unknown response recovery.
